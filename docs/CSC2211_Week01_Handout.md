## ส่วนที่ 2: บทนำ — ปุ่มสวยแต่ใช้งานไม่ได้

ลองนึกภาพระบบจองห้องของมหาวิทยาลัย ปุ่ม "จอง" ใหญ่ สีเด่น ตัวอักษรอ่านง่าย ดูเป็นระบบที่ออกแบบมาดี แต่นักศึกษาต้องเปิดห้องทีละหน้าเพื่อดูว่าห้องใดว่างเวลาใด กว่าจะรู้ว่าห้องที่ต้องการไม่ว่างก็เสียเวลาไปหลายนาที

ปุ่ม "จอง" **ไม่ใช่ปัญหา** ปัญหาอยู่ที่ **ลำดับงานและการแสดงข้อมูล** ถ้าเราแก้ด้วยการเปลี่ยนสีปุ่มหรือขยายตัวอักษร ปัญหาจะไม่หายไป นี่คือหัวใจของสัปดาห์นี้ นักออกแบบที่ดีต้อง **แยกให้ออก** ว่าอะไรคือปัญหาประสบการณ์ (UX) และอะไรคือรายละเอียดของส่วนติดต่อ (UI) เพื่อไม่ลงมือแก้ผิดที่

> **เส้นทางของรายวิชา** สัปดาห์ที่ 01 สร้างพื้นฐานและฝึกมองหาปัญหา → สัปดาห์ที่ 02 เก็บหลักฐานจากผู้ใช้จริงด้วยการสัมภาษณ์ → สัปดาห์ที่ 03–07 สังเคราะห์ ออกแบบโครงสร้าง และสร้าง wireframe → สัปดาห์ที่ 11–14 ต้นแบบ ทดสอบ และปรับแบบ

## ส่วนที่ 3: UX และ UI คืออะไร

### 3.1 นิยาม

**ประสบการณ์ผู้ใช้ (User Experience: UX)** คือประสบการณ์ทั้งหมดของผู้ใช้ตั้งแต่เริ่มต้นจนบรรลุเป้าหมาย ครอบคลุมความรู้สึก ความคาดหวัง ความสะดวก และผลลัพธ์ มาตรฐาน ISO 9241-210 นิยาม UX ว่าเป็นการรับรู้และการตอบสนองของบุคคลที่เกิดจากการใช้หรือการคาดว่าจะใช้ผลิตภัณฑ์ ระบบ หรือบริการ

**ส่วนติดต่อผู้ใช้ (User Interface: UI)** คือองค์ประกอบที่ผู้ใช้มองเห็นและโต้ตอบด้วย ได้แก่ ปุ่ม ป้ายกำกับ ช่องกรอกข้อมูล เมนู สี ตัวอักษร ไอคอน และข้อความแจ้งผล

| มุมมอง | UX | UI |
|---|---|---|
| คำถามหลัก | ผู้ใช้ทำงานสำเร็จหรือไม่ ใช้ขั้นตอนเท่าไร รู้สึกอย่างไร | หน้าจอมีองค์ประกอบอะไร แต่ละอย่างหน้าตาและทำงานอย่างไร |
| ขอบเขต | ทั้งเส้นทาง ก่อน–ระหว่าง–หลังใช้งาน | ที่หน้าจอหรือจุดสัมผัสหนึ่ง ๆ |
| ตัวอย่างงาน | วิจัยผู้ใช้ ออกแบบเส้นทาง จัดโครงสร้างข้อมูล | ออกแบบปุ่ม สี ตัวอักษร คอมโพเนนต์ |
| ตัวอย่างปัญหา | ต้องเปิดหลายหน้าจึงรู้ว่าห้องว่าง | ปุ่มยกเลิกสีเหมือนปุ่มจอง กดผิดง่าย |

> **ข้อควรจำ** UX และ UI ไม่ได้แยกขาดจากกัน UI ที่ดีเป็นส่วนหนึ่งของ UX ที่ดี แต่ UI ที่สวยไม่ได้รับประกันว่า UX จะดี

### 3.2 องค์ประกอบ UI ที่พบบ่อย

| กลุ่ม | ตัวอย่างองค์ประกอบ | หน้าที่ |
|---|---|---|
| การนำทาง | เมนู แท็บ breadcrumb | พาผู้ใช้ไปยังส่วนที่ต้องการ |
| การป้อนข้อมูล | ช่องข้อความ ตัวเลือก ปฏิทิน | รับข้อมูลจากผู้ใช้ |
| การกระทำ | ปุ่ม ลิงก์ | ให้ผู้ใช้สั่งงาน |
| ข้อมูลและป้ายกำกับ | ป้าย ข้อความช่วยเหลือ ไอคอน | อธิบายว่าสิ่งนั้นคืออะไร |
| ข้อความแจ้งผล | ข้อความสำเร็จ ข้อผิดพลาด การยืนยัน | บอกสถานะของระบบ |
| รูปลักษณ์ | สี ตัวอักษร ระยะห่าง | สื่อลำดับความสำคัญและอารมณ์ |

### 3.3 ห้าระนาบของประสบการณ์ผู้ใช้ (Garrett's Five Planes)

Jesse James Garrett แบ่งงานออกแบบเว็บและผลิตภัณฑ์ดิจิทัลเป็น 5 ระนาบ จากนามธรรมไปสู่รูปธรรม

```
 Surface   (ผิว)        รูปลักษณ์: สี ตัวอักษร ภาพ          ← UI ส่วนใหญ่
 Skeleton  (โครงร่าง)   การจัดวางองค์ประกอบ การนำทาง          ← UI/UX
 Structure (โครงสร้าง)  ลำดับงาน สถาปัตยกรรมสารสนเทศ          ← UX
 Scope     (ขอบเขต)     ฟีเจอร์และความต้องการเนื้อหา           ← UX
 Strategy  (กลยุทธ์)    เป้าหมายของผู้ใช้และของธุรกิจ          ← UX
```

ปัญหาที่ระนาบล่าง (กลยุทธ์ ขอบเขต โครงสร้าง) แก้ด้วยการปรับระนาบบนไม่ได้ ตัวอย่าง RoomRERU ปัญหา "ต้องเปิดหลายหน้า" เป็นปัญหาโครงสร้าง ไม่ใช่ปัญหาผิว

## ส่วนที่ 4: วิธีแยกปัญหา UX จากปัญหา UI

### 4.1 คำถามทดสอบ 3 ข้อ

เมื่อพบจุดติดขัดหนึ่งจุด ให้ถามตามลำดับ

1. **ถ้าแก้เพียงสี ขนาด ข้อความ หรือตำแหน่งขององค์ประกอบหนึ่งชิ้น ปัญหาจะหายไปหรือไม่** ถ้าหาย → น่าจะเป็นปัญหา **UI**
2. **ถ้าต้องเปลี่ยนลำดับขั้นตอน จำนวนหน้า การจัดกลุ่มข้อมูล หรือข้อมูลที่แสดง** → น่าจะเป็นปัญหา **UX (โครงสร้าง/ลำดับงาน)**
3. **ถ้าระบบทำสิ่งที่ผู้ใช้ไม่ได้ต้องการเลย หรือขาดความสามารถสำคัญ** → น่าจะเป็นปัญหา **UX (ขอบเขต/กลยุทธ์)**

### 4.2 ตัวอย่างพร้อมวิธีคิด: RoomRERU

| จุดติดขัดที่สังเกต | ถามข้อ 1 | จำแนก | เหตุผล |
|---|---|---|---|
| ต้องเปิดห้องทีละหน้าจึงทราบว่าห้องว่างเมื่อใด | แก้สีหรือข้อความไม่ช่วย | **UX (โครงสร้าง/การแสดงข้อมูล)** | ต้องแสดงห้องว่างรวมในหน้าเดียว |
| ปุ่มยกเลิกสีเหมือนปุ่มจอง | แก้สีแล้วหาย | **UI** | ปัญหาที่ระนาบผิว |
| จองสำเร็จแล้วไม่มีข้อความยืนยัน | เพิ่มข้อความช่วยได้ แต่ต้องวางลำดับงานให้มีขั้นยืนยัน | **ทั้ง UI และ UX** | เป็นสถานะของระบบที่ขาดหายและกระทบความมั่นใจ |
| ต้องล็อกอินใหม่ทุกครั้งที่ดูห้อง | เปลี่ยนปุ่มไม่ช่วย | **UX (ลำดับงาน)** | ผูกกับกลไกยืนยันตัวตน |
| ตัวอักษรบอกเวลาเล็กมากบนมือถือ | ขยายตัวอักษรแล้วหาย | **UI** | ปัญหาที่ระนาบผิว (และการเข้าถึง) |

> **สังเกต** บางปัญหาก้ำกึ่ง การจำแนกควรมี "เหตุผล" ประกอบเสมอ ไม่ใช่ตอบแค่ว่า UX หรือ UI

### 4.3 เชื่อมกับหลักการใช้งาน: 10 Usability Heuristics ของ Nielsen

Jakob Nielsen เสนอหลักการ 10 ข้อ ใช้เป็น "ภาษากลาง" เพื่ออธิบายว่าจุดติดขัดละเมิดหลักการใด

| # | หลักการ | ตัวอย่างใน RoomRERU |
|---|---|---|
| 1 | การมองเห็นสถานะของระบบ | ไม่มีข้อความยืนยันหลังจอง |
| 2 | ความสอดคล้องกับโลกจริง | ใช้คำว่า "slot" แทน "ช่วงเวลา" |
| 3 | ผู้ใช้ควบคุมและมีอิสระ | ยกเลิกหรือแก้ไขการจองไม่ได้ |
| 4 | ความสม่ำเสมอและมาตรฐาน | ปุ่มบางหน้าชื่อ "จอง" บางหน้าชื่อ "ยืนยัน" |
| 5 | การป้องกันข้อผิดพลาด | เลือกเวลาทับกับคนอื่นได้ แล้วค่อยแจ้งผิดพลาด |
| 6 | การจดจำดีกว่าการจำ | ต้องจำรหัสห้องเอง ไม่มีรายการให้เลือก |
| 7 | ความยืดหยุ่นและประสิทธิภาพ | ไม่มีทางลัดสำหรับจองห้องเดิมซ้ำ |
| 8 | การออกแบบเรียบง่าย | หน้าแรกมีลิงก์ 30 อัน |
| 9 | ช่วยให้รู้จักและกู้คืนจากข้อผิดพลาด | ข้อความผิดพลาดเป็นรหัส "Error 500" |
| 10 | ความช่วยเหลือและเอกสาร | ไม่มีคำอธิบายกฎการจอง |

### 4.4 คุณลักษณะของการใช้งานได้ (Usability)

Nielsen ระบุ 5 มิติที่ใช้วัดความง่ายในการใช้งาน ได้แก่ **เรียนรู้ได้ง่าย** (learnability) **มีประสิทธิภาพ** (efficiency) **จดจำได้ง่าย** (memorability) **มีข้อผิดพลาดน้อย** (errors) และ **พึงพอใจ** (satisfaction) ใช้เป็นหัวข้อตรวจตอนบันทึกจุดติดขัด

## ส่วนที่ 5: การเริ่มจากผู้ใช้ เป้าหมาย และบริบท

หลักการสำคัญของใบความรู้คือ "การออกแบบเริ่มจากเป้าหมายและบริบทของผู้ใช้" ไม่ใช่จากฟีเจอร์ที่ระบบมี

| องค์ประกอบ | คำถามนำ | ตัวอย่าง RoomRERU |
|---|---|---|
| ผู้ใช้ | ใครใช้ มีลักษณะอย่างไร | นักศึกษาปี 2 ที่ต้องประชุมกลุ่มส่งงาน |
| เป้าหมาย | ต้องการบรรลุอะไร (ไม่ใช่ "อยากกดอะไร") | จองห้องติวให้ทีม 5 คนในเย็นวันพรุ่งนี้ให้เสร็จก่อนเลิกเรียน |
| บริบท | ใช้ที่ไหน เมื่อไร ด้วยอุปกรณ์ใด อะไรรบกวน | ใช้มือถือระหว่างเดินไปห้องเรียน สัญญาณไม่แรง เวลาเหลือ 3 นาที |
| ข้อจำกัด | ข้อจำกัดด้านทักษะ เวลา เครือข่าย การเข้าถึง | ไม่ทราบรหัสห้อง ไม่ต้องการล็อกอินหลายรอบ |

**ผลต่อการออกแบบ** ถ้าบริบทคือมือถือและเวลาน้อย การแก้ที่ UI อย่างเดียว (เช่น ปรับสี) ไม่ช่วยเท่าการลดขั้นตอน

> เราจะทำอย่างไรให้ **[ผู้ใช้]** สามารถ **[เป้าหมาย]** ได้ **[เกณฑ์ที่วัดได้]**

**ตัวอย่าง:** นักศึกษาที่ต้องจองห้องติวด่วนด้วยมือถือต้องเปิดข้อมูลห้องทีละหน้าเพื่อหาห้องว่าง ทำให้ใช้เวลานานและยอมแพ้ เราจะทำอย่างไรให้นักศึกษาหาห้องว่างและจองสำเร็จได้ภายใน 3 ขั้นตอน

> **ข้อควรระวัง** โจทย์ที่ดีไม่ระบุวิธีแก้ในตัวโจทย์ (เช่น "ทำแอปใหม่") และไม่กว้างเกินไป (เช่น "ทำให้ระบบดีขึ้น")

## ส่วนที่ 6: ขั้นตอนการทำงานทดลองใช้บริการและบันทึกจุดติดขัด

### 6.1 ภาพรวม 7 ขั้นตอน

```
① เลือกบริการ → ② นิยามผู้ใช้/เป้าหมาย/บริบท → ③ ทดลองใช้พร้อมบันทึกหน้าจอ
   → ④ บันทึกจุดติดขัด → ⑤ จำแนก UX/UI + หลักการ → ⑥ ให้ความรุนแรงและจัดลำดับ → ⑦ เขียนโจทย์โครงงาน
```

### 6.2 รายละเอียดแต่ละขั้น

| ขั้น | สิ่งที่ทำ | ผลลัพธ์ |
|---|---|---|
| ① เลือกบริการ | เลือกบริการของมหาวิทยาลัยหนึ่งบริการ เช่น จองห้อง ลงทะเบียนเรียน ตรวจสอบเกรด ยืมหนังสือ ชำระค่าธรรมเนียม | ชื่อบริการและลิงก์ |
| ② นิยามผู้ใช้ | เขียนผู้ใช้ เป้าหมาย บริบท ข้อจำกัดอย่างละหนึ่งบรรทัด | การ์ดผู้ใช้สั้น ๆ |
| ③ ทดลองใช้ | ตั้งงาน 1 งาน (เช่น "จองห้องวันพรุ่งนี้ 16.00–17.00") เริ่มบันทึกหน้าจอและจับเวลา ทำจนสำเร็จหรือยอมแพ้ | ไฟล์บันทึกหน้าจอ เวลา และจำนวนคลิก |

## ส่วนที่ 7: จริยธรรม ข้อมูลส่วนบุคคล และการใช้ AI

### 7.1 ข้อมูลระบุตัวตนในหลักฐาน

รายการตรวจก่อนส่งของรายวิชาระบุว่า "เก็บข้อมูลผู้เข้าร่วมด้วยรหัสและตัดข้อมูลระบุตัวตนออกจากชิ้นงานที่แชร์" แม้สัปดาห์นี้นักศึกษาทดลองใช้เอง แต่ภาพหน้าจออาจมีชื่อ รหัสนักศึกษา เกรด หรือข้อมูลที่เกี่ยวกับผู้อื่น ให้ปิดบังก่อนส่ง และฝึกนิสัยนี้ไว้ใช้กับการวิจัยผู้ใช้ในสัปดาห์ที่ 02

> **กรอบกฎหมายที่เกี่ยวข้อง** พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) ของประเทศไทย กำหนดหลักการเก็บข้อมูลเท่าที่จำเป็นและต้องมีฐานทางกฎหมาย (เช่น ความยินยอม) ผู้สอนควรให้ข้อมูลเพิ่มเติมตามนโยบายมหาวิทยาลัย

### 7.2 การใช้ Generative AI ช่วยงาน UX

AI ช่วยระดมความคิด ร่างตาราง และตรวจภาษาได้ แต่ **ห้ามใช้แทนการทดลองใช้งานจริง** เพราะจุดติดขัดต้องมาจากหลักฐานที่นักศึกษาเก็บเอง

**ตัวอย่าง prompt ที่ดี**

```
ฉันบันทึกจุดติดขัดนี้จากการทดลองใช้ระบบจองห้อง: "ต้องเปิดห้องทีละหน้าจึงรู้ว่าห้องว่างเมื่อใด"
ช่วยถามคำถามเพื่อให้ฉันตัดสินว่าเป็นปัญหา UX หรือ UI และเสนอหลักการ Nielsen ที่เกี่ยวข้อง
อย่าตัดสินแทนฉัน และอย่าเสนอวิธีแก้จนกว่าฉันจะขอ
```

**สิ่งที่ห้ามทำ:** ให้ AI "สร้างจุดติดขัด" ที่ไม่ได้พบจริง ส่งภาพหน้าจอที่ไม่ได้ถ่ายเอง หรือนำข้อมูลระบุตัวตนเข้าเครื่องมือ AI

### 7.3 Academic Integrity

ส่งหลักฐานจากการทดลองใช้ของตนเอง ระบุเครื่องมือ AI ที่ใช้และสิ่งที่ปรับแก้ไว้ใน AI Log ท้ายงาน

## ส่วนที่ 9: แบบฝึกหัดและแบบฝึกปฏิบัติ

### 9.1 คำถามท้ายบท (8 ข้อ)

**ข้อ 1.** อธิบายความแตกต่างระหว่าง UX และ UI ด้วยคำพูดของตนเอง พร้อมยกตัวอย่างอย่างละหนึ่งข้อ

> **แนวตอบ:** UX คือประสบการณ์ทั้งเส้นทางจนบรรลุเป้าหมาย (เช่น ใช้กี่ขั้นตอนจึงจองห้องสำเร็จ) UI คือองค์ประกอบที่โต้ตอบด้วย (เช่น ปุ่ม จอง ป้ายกำกับ สี)

**ข้อ 2.** จากตัวอย่างในใบความรู้ ผู้ใช้อ่านปุ่มจองได้ชัดแต่ต้องเปิดหลายหน้าจึงทราบว่าห้องว่าง ปัญหาอยู่ที่ UX หรือ UI เพราะเหตุใด

> **แนวตอบ:** UX (ลำดับงานและการแสดงข้อมูล) เพราะปุ่มอ่านได้ชัดแล้ว การปรับสีหรือขนาดปุ่มไม่ช่วยให้รู้ว่าห้องว่างเร็วขึ้น ต้องปรับการแสดงข้อมูล เช่น แสดงห้องว่างรวมในหน้าเดียว

**ข้อ 3.** จำแนกว่าเป็นปัญหา UX หรือ UI พร้อมเหตุผล (ก) ปุ่มยกเลิกกับปุ่มจองสีเหมือนกัน (ข) ต้องกรอกข้อมูลเดิมซ้ำสามหน้า (ค) ตัวอักษรเล็กจนอ่านไม่ออกบนมือถือ

> **แนวตอบ:** (ก) UI — แก้สี/รูปแบบแล้วหาย (ข) UX — ต้องปรับลำดับงานให้กรอกครั้งเดียว (ค) UI — ขยายตัวอักษร (และเป็นประเด็นการเข้าถึง)

**ข้อ 4.** ห้าระนาบของ Garrett แต่ละระนาบเกี่ยวข้องกับอะไร และปัญหา "ต้องเปิดหลายหน้า" อยู่ระนาบใด

> **แนวตอบ:** กลยุทธ์ (เป้าหมาย) ขอบเขต (ฟีเจอร์) โครงสร้าง (ลำดับงาน/สถาปัตยกรรมสารสนเทศ) โครงร่าง (การจัดวาง/นำทาง) ผิว (รูปลักษณ์) ปัญหานี้อยู่ที่ระนาบโครงสร้าง

**ข้อ 5.** จงเขียนผู้ใช้ เป้าหมาย และบริบทของบริการ "ตรวจสอบเกรดออนไลน์" อย่างละหนึ่งบรรทัด

> **แนวตอบ (ตัวอย่าง):** ผู้ใช้ = นักศึกษาปี 1 ที่รอผลสอบ; เป้าหมาย = ดูเกรดรายวิชาที่ประกาศแล้วโดยไม่ต้องถามอาจารย์; บริบท = ใช้มือถือตอนกลางคืน ล็อกอินด้วยรหัสนักศึกษา ผลเข้ามาพร้อมกันหลายคนทำให้ระบบช้า (คำตอบอื่นที่สมเหตุสมผลยอมรับได้)

**ข้อ 6.** ข้อความผิดพลาด "Error 500" ละเมิดหลักการของ Nielsen ข้อใด และเป็นปัญหา UX หรือ UI

> **แนวตอบ:** ข้อ 9 (ช่วยให้รู้จักและกู้คืนจากข้อผิดพลาด) และอาจข้อ 2 (ใช้ภาษาของผู้ใช้) เป็นทั้ง UI (ข้อความ) และ UX (ผู้ใช้ไม่รู้ว่าต้องทำอะไรต่อ) ควรอธิบายเหตุผลประกอบ

**ข้อ 7.** จงให้คะแนนความรุนแรง (0–4) และให้เหตุผล: ระบบจองห้องไม่ยืนยันการจองสำเร็จ ผู้ใช้จึงจองซ้ำสามครั้ง

> **แนวตอบ (ตัวอย่าง):** 3 — เจอบ่อย (ทุกครั้งที่จอง) ผลกระทบสูง (จองซ้ำ เสียเวลาและสร้างการจองทับ) และผู้ใช้ไม่รู้วิธีเลี่ยง (ยอมรับ 3–4 พร้อมเหตุผลที่สอดคล้องกับเกณฑ์)

**ข้อ 8.** เขียนโจทย์โครงงานจากจุดติดขัด "ต้องเปิดห้องทีละหน้าจึงทราบว่าห้องว่าง" โดยไม่ระบุวิธีแก้

> **แนวตอบ (ตัวอย่าง):** เราจะทำอย่างไรให้นักศึกษาที่ต้องจองห้องด่วนด้วยมือถือหาห้องว่างในช่วงเวลาที่ต้องการและจองสำเร็จได้ภายใน 3 ขั้นตอน (ไม่ใช้โจทย์ที่ระบุว่า "ทำแอปแสดงปฏิทินรวม" เพราะเป็นการระบุวิธีแก้)

### 9.2 แบบฝึกปฏิบัติ A: จำแนกจุดติดขัด (ข้อมูลจำลอง)

บันทึกการทดลองใช้ระบบ "ลงทะเบียนชมรม" (ข้อมูลจำลองสำหรับฝึก) มีจุดติดขัด 5 จุด

| # | จุดติดขัด |
|---|---|

### 9.3 แบบฝึกปฏิบัติ B: ใบงานสัปดาห์ที่ 01 (ส่งงาน)

**กิจกรรมปฏิบัติ** เลือกบริการมหาวิทยาลัยหนึ่งบริการ ระบุผู้ใช้ เป้าหมาย และจุดติดขัดสามจุดจากการทดลองใช้งาน

**สิ่งที่ส่ง** บันทึกหน้าจอพร้อมคำอธิบาย จุดติดขัดสามจุด และโจทย์โครงงานหนึ่งข้อ

**รายการตรวจก่อนส่ง** ตรวจความครบถ้วนของชิ้นงาน ความเชื่อมโยงกับโจทย์หรือหลักฐาน และความชัดเจนของเหตุผล เก็บข้อมูลผู้เข้าร่วมด้วยรหัสและตัดข้อมูลระบุตัวตนออกจากชิ้นงานที่แชร์

**เช็กลิสต์ก่อนส่ง**

- [ ] เลือกบริการ 1 บริการ เขียนผู้ใช้ เป้าหมาย บริบท ครบ
- [ ] มีบันทึกหน้าจอ (หรือภาพต่อเนื่อง) พร้อมคำอธิบายและเวลา
- [ ] จุดติดขัด 3 จุด แต่ละจุดมีหลักฐาน จำแนก UX/UI พร้อมเหตุผล และให้ความรุนแรง
- [ ] โจทย์โครงงาน 1 ข้อ เชื่อมกับจุดติดขัดสำคัญสุดและไม่ระบุวิธีแก้
- [ ] ปิดบังชื่อ รหัส อีเมล และข้อมูลระบุตัวตนในภาพ
- [ ] ระบุการใช้ AI (ถ้ามี) ท้ายงาน

### หมายเหตุสำหรับอาจารย์ผู้สอน

1. **ลำดับเวลาที่แนะนำ (รวม 3 ชั่วโมง):** บทนำและกิจกรรม 1 (25 นาที) → ส่วนที่ 3–4 (35) → ส่วนที่ 5 และกิจกรรม 3 (25) → ทดลองใช้และบันทึก (50) → จำแนกและให้ความรุนแรง (25) → Pitch โจทย์ (20)
2. **จุดที่นักศึกษาสับสนบ่อย:** คิดว่า UX = การออกแบบหน้าตา, เขียนโจทย์ที่ระบุวิธีแก้, จดจุดติดขัดเป็นความรู้สึก ("ไม่สวย") แทนที่จะเป็นพฤติกรรมที่สังเกตได้
3. **ข้อควรระวังด้านจริยธรรม:** ย้ำให้เลือกบริการที่ไม่ต้องเปิดเผยข้อมูลผู้อื่น และห้ามทดลองทำธุรกรรมที่มีผลจริง (เช่น ชำระเงิน) เกินความจำเป็น
4. **เชื่อมไปสัปดาห์ที่ 02:** ปิดคาบด้วยคำถาม "จุดติดขัดที่เราพบเกิดจากการสังเกตของเราเอง ผู้ใช้คนอื่นเจอเหมือนกันหรือไม่" นำไปสู่การสัมภาษณ์ผู้ใช้
5. **หมายเหตุเกี่ยวกับเนื้อหา:** ตัวอย่างและแบบฝึกหัดนอกเหนือจากใบความรู้ต้นฉบับ (RoomRERU, ลงทะเบียนชมรม) เป็นข้อมูลจำลองที่เพิ่มเพื่อประกอบการสอน
